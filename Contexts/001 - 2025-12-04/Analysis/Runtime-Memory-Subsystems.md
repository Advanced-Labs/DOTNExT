# .NET Runtime Memory Subsystems Analysis

> **Document Type:** Technical Analysis
> **Version:** 1.0
> **Date:** 2025-12-06
> **Source:** AI analysis of CLR architecture + DOTNExT design implications

---

## 1. Core Insight: GC ≠ Memory System

The .NET "memory system" is **not** just the GC. The full memory story involves multiple cooperating subsystems:

> **GC + JIT + EE + Loader + Handle system**, sitting on top of the OS VM.

The GC owns the **managed object graph** and its lifetime, but the **full memory story** is wider.

---

## 2. The Three-Layer Model

### Layer 1: OS / Hardware
- Virtual memory, pages, stacks, native heaps
- CLR is just another native process from the OS point of view

### Layer 2: CLR / CoreCLR Runtime
- Native code (C/C++) that:
  - Reserves/commits memory from the OS
  - Manages **managed heaps**, threads, JIT, loader, etc.
- Inside this, you have several subsystems; the **GC** is one of them

### Layer 3: Managed World (IL, C#, etc.)
- Managed objects, references, arrays, `new`/`newobj`, `stackalloc`, etc.
- No direct pointer to OS memory (unless `unsafe`)

---

## 3. Memory Subsystems Breakdown

### 3.1 Managed Heap (GC-Side)

**GC Heap Segments:**
- Ephemeral segments (Gen0/1)
- Full segments (Gen2)
- LOH segments (Large Object Heap)
- POH segments (Pinned Object Heap - recent addition)

**Per-Thread Allocation Buffers (TLABs / Allocation Contexts):**
- When code does `new Foo()`, it usually just bumps a pointer in a per-thread buffer
- If the buffer is full, falls back into the GC allocator to refill

**GC Responsibilities:**
- Managed heap layout & allocation
- Generational heaps: Gen0, Gen1, Gen2, LOH, POH
- Reclamation & compaction (mark, sweep/compact)
- Updating references during compaction
- Interaction with JIT (GC info tables)

**What GC Does NOT Do:**
- Does not talk to the OS directly for everything – that's done via the runtime's memory manager layer
- Doesn't own **all** memory used by the process
- JITted code, metadata, loader heaps, handle tables, and interop allocations are managed by other parts

### 3.2 Thread Stacks

- Each managed thread has a standard **native stack**
- JIT and runtime cooperate to make that stack **GC-aware**:
  - At safe points, runtime knows which stack slots are references
  - GC info tables generated by JIT for each method

### 3.3 Runtime / Loader Heaps

Large chunks of memory that are **not on the GC heap**:

| Heap | Contents |
|------|----------|
| **Loader heaps** | Type metadata (MethodTable, vtables, interface maps), EE internal structures |
| **JIT code heap** | JITted machine code |
| **Handle tables** | Strong, weak, pinned, etc. handles for interop, `GCHandle`, finalization |
| **Interop/native** | `Marshal.AllocHGlobal`, COM wrappers, P/Invoke marshaling buffers |

## 4. VES: Spec vs Implementation

### VES (Virtual Execution System) - Spec Level
- A **concept / abstract machine** defined in ECMA-335 CLI spec
- NOT a specific DLL or piece of code
- Defines:
  - Loading & verifying assemblies and metadata
  - Executing IL
  - Enforcing **type safety and memory safety**
  - Providing a **garbage-collected heap**
  - Evaluation stack, locals, arguments, etc.

### CLR/CoreCLR - Implementation Level
- Concrete implementation of VES
- Provides: GC heap, generations, LOH/POH, JIT, loader, etc.
- Talks to OS virtual memory
- Enforces GC-safety at IL boundaries

### What VES Spec Defines vs Leaves Open

**VES Defines:**
- You have a managed heap
- Objects accessed via object references, not raw pointers
- VES keeps references valid (no dangling pointers, no use-after-free)
- VES provides a garbage collector (algorithm unspecified)

**VES Does NOT Dictate:**
- How many generations
- Exact algorithms (mark-sweep, copying, concurrent, etc.)
- How the implementation talks to the OS

---

## 5. Summary Formula

> The ".NET memory system" is the **CLR's implementation of the VES's memory semantics**:
> GC + object model + stacks + loader heaps + JIT code + interop heaps.

## 6. Implications for DOTNExT Design

### 6.1 Memory Systems to Study/Integrate

| System | Current Owner | DOTNExT Consideration |
|--------|--------------|----------------------|
| **GC Heap** (Gen0/1/2, LOH, POH) | GC | MOM wraps this, adds UUID tracking |
| **Loader Heaps** | EE/Loader | CMS should track; type metadata = Engram candidates |
| **JIT Code Heap** | JIT | Memantics wants to store code; understand this heap |
| **Handle Tables** | Runtime | Weak/strong handles map to Engram reference types |
| **TLABs/Allocation Contexts** | GC | MOM needs to intercept here for UUID assignment |
| **Stacks** | Runtime/JIT | GC info tables track roots; ORION could leverage |

### 6.2 Key Insight: GC Info Tables

> "The JIT generates GC info tables: for each safe point, which registers/stack slots hold references."

This is similar to CGCDesc but for stack frames. The runtime already tracks:
- Which stack slots are references
- At which program points

**Implication:** Stack-based references could feed into ORION for temporary relationship tracking during method execution - not just heap relationships.

### 6.3 Loader Heaps = Type Engrams

Type metadata structures live in loader heaps, not GC heap. For Memantics' vision of storing types as Engrams:
- Types are already "objects" in loader heap memory
- They have structure (MethodTable, EEClass)
- They could be given UUIDs and serialized

**Question:** Can loader heap structures be extracted as Engrams? This would enable type versioning and code-as-data.

### 6.4 Handle Tables → Reference Types

The runtime already has:
- Strong handles
- Weak handles (short/long)
- Pinned handles
- Dependent handles

These map naturally to Engram reference semantics:
- Internal reference ≈ strong handle behavior
- Lazy reference ≈ weak handle (resolve on demand)
- Proxy ≈ dependent handle (lifetime tied to something else)

**Opportunity:** Don't reinvent reference tracking; extend handle table concepts.

### 6.5 TLABs as UUID Assignment Point

Per-thread allocation buffers are where most allocations actually happen (bump pointer). To assign UUIDs at allocation:

| Option | Approach | Trade-off |
|--------|----------|-----------|
| **A** | Intercept after TLAB bump, before returning to user | Every allocation pays cost |
| **B** | Modify TLAB refill to pre-assign UUID batch | Amortized cost, complexity |
| **C** | Lazy UUID assignment (first time object needs it) | Zero cost until needed |

**Recommendation:** Option C (lazy) is probably wisest - not every object needs a UUID immediately.

## 7. Integration Recommendations

### 7.1 Map CMS to Native Runtime Memory Layer
- CMS isn't replacing these systems; it's the unified view across them
- CMS tables parallel what the runtime already tracks, but with Engram semantics

### 7.2 Extend Handle Tables, Don't Replace
- Add new handle types for Engram references
- Leverage existing weak/strong/dependent semantics

### 7.3 Study GC Info Tables for Stack Relationship Tracking
- Could enable "live relationship view" during execution
- Useful for debugging, tracing, possibly AI observability

### 7.4 Loader Heap Integration is Key for Memantics
- If types become Engrams, loader heaps are the source
- Need to understand MethodTable/EEClass extraction

### 7.5 JIT Code Heap = Future Code Storage
- Memantics storing IL/compiled code means understanding this heap
- Potentially: store code Engrams, JIT on demand from Memantics

## 9. Key Takeaway

> DOTNExT's CMS needs to be aware of **all** these memory subsystems, not just the GC heap.

The good news: the runtime already has infrastructure (handle tables, GC info, loader heaps) that can be **extended rather than replaced**.
