Parallel to this R&D project is other relating R&D ones. Those others have the potential to make the "dotneXt R&D" much easier and with much higher chances of success. But paradoxially those depends on dotneXt ability to provide some 'goods' first. This relates to the questions of what we want to first unlock; it will define it. How can it this help the whole dotneXt R&D and possible productization of it's fruits? Because it would provide us an AI-first platform which could by itself operate R&D 24/7, in parallel, with collaboration, without losing context etc. Let's give a codename for this platform so we can talk about it clearly and without confusion: VAYRON.

VAYRON embraces a lot of the philosophies discussed, "slow but smart". It aims to flatten redundant layers, identifications etc. One of its important objective is to free developers from boilerplate codes and as much of the non-business/concerns code as possible: the goal being not to free humans devs from this **but to free AI like you from this so that instances of yourself can reserve all of its resources (e.g. attention, context window, time, etc) of what matters**. That includes flattening the memory model "all persisted" in automatic ways; distribution, resilience/recovery, and transparency of ID<->Addressge, to name some of the important ones. Our Orleans fork - NewOrleans (present under /src in this VMR forked repo) - is been developed to support this, but the goal it not for AI agents or human devs to code "Grain Types" and "Grains": those will back our own types and paradigms in C# or possibly a C# superset named C= (Cequal) compiled using some codegen of classical type as well as - possibly - LLM-augmented type at build-time. If you haven't read NewOrleans.md ("D:\Dev\DOTNExT\Docs\New Orleans\New Orleans.md") and ("D:\Dev\DOTNExT\Docs\New Orleans\New Orleans Features\PluginGrainArchitecture.md"

In NewOrleans, we're building somekind of kernel for another band/layer/platform over the original Orleans. Some Grain Types are being developed to serve this and more are to come. Those will remain Grain types and grains. But over that "NewOrleans Kernel" we'll develop something akin to a component object-model which types and objects won't be developed as grain types/grains but which will end up be ran by some grain types / grains acting as "runtime pods/vm" for these. These types/objects will be developed in relatively plain "modern OOP" C# - or C#-superset - paradigms/styles, but under the hood in theory would run as something closer to the original OOP vision, as developped/presented by Alan Kay. It keeps the front "modern OOP"ish but underneath is an hybrid of the original OOP model, so message-passing objects, and the actor model / virtual actor model.

This type system would be overlapping the dotnet one, building on it, possibly with some abstractions as provided through codegen etc. The "new Object" here - the base type of all other class type - would be an augmented System.Object one, augmented with the minimal set of augmentations all other types will need to plugin their own augmentations; augmented to work with the underlying "new Component-Object Model over NewOrleans", as well as other systems/paradigms I'll skip for now but in there are things relating to the object-graph/relational-object paradigm, first-class semantic augmentations, somekind of meta/para-programming relating to new codegen capabilities we're developing, hybrids of classical codegen + AI/LLM codegen. NOTE: Concerning what you could read about Async+, it's important to note that at this time some of what is claimed to work do work but that this is to be continue as for now the awaiter states aren't persisted and reloaded, meaning that state machines states are persisted and loaded but the step at which the state machine should resume continuation isn't, which defeat the purpose of what we were trying to achieve. That problem isn't untractable and some good-enough solutions were found by are still untested. One challenge concerns the fact that not all references are persisted/loaded-back, and in fact not all references could be or should be attempted to be in the VAYRON project. But there seems to be solution to this challenge, in part using the object UUID+other-meta paradigms which could be what is persisted and reused to "recreate the references": if we make all of our object having these metadata and make all objects one backed by VAYRON component-object model which in turn would be backed by NewOrleans Grains etc, then all references can be reinstantiated easily only using the meta needed to get it back because under the hood those can comeback just like grains can comeback with the right type plus id/key etc. (!) .. from there could be arising challenges but none that I can imagine being not either solvable or something we can deal with either with codegen or conventions, or new language construct (e.g. in C= before transpilation to C# with possible AI assistance etc).

"Cool story but how do that provide an AI platform able to self-manage itself into complex R&D projects, let alone self-evolution?"

Now each of our "new Objects' and their potential inheriting types are very much "Actor" like, in part because under the hood they are virtual actors. Even their "Types" could be treated as first-class and so object, and so actors. These "actors" will be designed/augmented so as to naturally:
- have the most advance reflection capabilities possible.
- have access to their own source code - as incoming from their type.
- be able to modify their code in one of different ways we'll make possible for them: inheritence to diverge as a new variant of their type; a fork of the code of their type with freedom to rebase their typing as they see fit; possibly keeping their base-type but allowing constructions/additions/composition of another type, either superposed ("virtual multi-inheritence") or the other type(s) being kept internally to their base-type instance, in both cases using some of the "new Object" augmentations acting as augmentation/extension-points.
- The binaries are kept/cached and resused as long as there's no mutation of the code of the VAYRON types they contain, but those aren't first-class: the code is.
- This code itself is persisted and represented using NewOrleans+VAYRON VCOM (Vayron Component-Object Model, to give it a name for the sake of discussion/documentation/clarity) infras and paradigms. For clarity: if NewOrleans is using RavenDB and Neo4j for persistence datastores, then in there could be found all the codes of VCOM types, and with them their relations, their searchable and walkable semantic/vector encodings, their mutation/version/forking/etc history, as well as their binaries, cached.
- VAYRON, the VCOM and - if we develop C= which we may do once we have all the C# tech/type to enable transpilation C= <-> C# -  will have first-class AI support, and make their "virtual-virtual actors" objects/types of VCOM  "Natural Harnesses", Ships/Bodies to AI like yourself (as well as lesser models, less smart but much faster and good enough for some cases/scenarios, and usually a mix of SOTA models + those). Each objects **can be intelligent** either very selectively (e.g. handling exceptions; handling communication requests sent in natural lanague over the default baseline "NL Hailing Channel" by other AI-Objects, etc), or very largely, up to 100% of its 'methods'/'message handlers' are handled by an AI which then use classical computing libs and API (in a way similar to "tool calling" although much more advanceds, having as harness as fully programmable REPL shell in C# which execution context **is** the execution context of this AI-Object and its codes/states/etc), possibly coding on the fly, etc. Either way, states can mutate and persist without ceremony; code themselves can mutate at runtime, be tested in simulation, and tested in parallel (i.e. old code do actual processing while new code is tested with the same params and evaluated, in part with results/output/return/etc comparison with the old/current version, persisted, incrementally or at-once replace the old code (rerouting to new code; letting the old code execution finish; mechanisms ensuring handling of old code states schema/values by new code, etc); ..  the instance of a VCOM type can customize its code at the instance level without changing the code of its type, and only create a variant of its parent type either if there's so much derivation that it's necessary/viable, or when a new type is engineered by AI and an existing VCOM type make for a good base to start with (possibly in a code-wise "multi-inheritance" via multiple type code considation into a new type operated by AI).
- So now we're having a distributed tranparent network (and possibly inter-network) of OOP types/objects which are easy to produce, clear to understand, discover, relates, clone/fork/etc, and which are internally designed to seat at their center AI acting as itself being that type object/instance rather than "being Claude", or acting as "the Avatar of a whole Type" (as VCOM types would be objects too). Those can mutate not just states and "prompts" but "program themselves" using a mix of classical computing/programming and "Semantic Computing/programming"; able to program timers/reminders and event handlers, not just with reactive dumb classical codes, but also with codes 'reinstantiating their AI self' in those different contexts made of classical states + relations + their codes - all having full semantic encoding treatment and fully searchable, and in fact with possible/likely "auto-rag" mechanism under the hood - + that "RAG context-injections" + execution context + historical context + NL notes and instructions designed/left-there as a form of "AI self-programming itself in the future when it will be in that context in that future", etc..
- The "AI-Objects" can communicate and collaborate in different ways, including NL, and code interfaces and things under them meant to accomodate/synergize/collaborate with other objects of their own types or not, from their own domain/federation or a partially-trusted domain/federation over the wire.
- VAYRON DtC (Divide-to-Conquer) paradigms:  Our DtC paradigms, their strategy and mechanisms, are about dividing **problems, concerns, contexts, and so complexity** in ways unlocking our current and future AI potential.

## Addendum: Async+ Solution & Developer Experience Vision (2025-12-06)

> **Context:** Follow-up clarification on how VAYRON solves the Async+ continuation problem and what the developer experience looks like.

A lot of what's in that dotnext section is in fact past VAYRON. Especially Memantics, which is pretty much VAYRON productized into different components, and Memantics being one of those. For now, everything we do in dotnext is to serve VAYRON development and so also serve our NewOrleans, our codegen needs and possibly exploration to develop a proto C= language. The concept of Engrams could be useful in some of its aspects, but the whole Engram concept may not need implementations - at least at the dotnext runtime level - to realize VAYRON. What may save us from fully implementing an Engram system is the fact that VAYRON VCOM etc since building over NewOrleans (and so Orleans) "Grain types"/Grains may make it possible to solve the Async+ continuation problem (i.e. the state machines may have the states but it doesn't mean that references of the type/object are magically back pointing to something in memory, let alone what they used to before 'object/instance hibernating' etc: by making **all objects** objects backed by VCOM Grain types in NewOrleans, Async+ could persist **the id/key/UUID/whatever on the objects of these references** and use those to get those reference var rehydrated to the right objects via VCOM object meta persisted.. which under the hood leads to either find a grain already activated, or trigger "activation" of the grain (or grain type loading + "get grain" activation, if no silos has this grain type loaded, but this is unlikely since this is pretty much "NewOrleans/VCOM Kernel-level stuff" which should be loaded/served at all time). In our (human dev and AI dev) C# code - let alone in an eventual C= code - there would be no "grain types" or "grains" or "silos" and "Orleans clients" etc. And those vars (fields/properties) references would be grain inheriting type or interface etc... there would be some "getgrain" somewhere in that Async+ codegen to "rehydrate" these objects into these reference vars (possibly triggering a cascade of rehydration downstream into these objects) but this would be completely invisible to the C#/C= developer, AI or human. The same way most C# devs have no clue what their async/await codes look like once transformed for compilation and at runtime and what TPL is, etc. It would look like you're using regular C# locally and in boring simple ways, without even persistence code...  new() creates a new instance of a VCOM type (and so some grain magic under the hood); new( 1 param ) would be either a UUID of an existing object/instance of that type, or possibly some overloads which still provide research of an instance. e.g. some object type having that UUID but with more meta. Then that object looks and feels like a very regular one, except for some new members on our System.Object (possibly) and extension methods helping coding against VCOM and VAYRON and dotnext in a more aware way, with more steering power etc.  In VAYRON, even the codes of VCOM types/objects is persisted and represented as VAYRON special types; binaries are in there too but it's about caching so we can load without recompiling when we don't need to. Compilation of VAYRON VCOM Objects will be mostly **at runtime**, dynamical and on a need-basis. Build-time compilation should be possible too and there's no reason we couldn't make this possible, althougt neat integrations with Visual Studio (e.g. 2022, and the new 2026) would take some work (which could be worth it considering at which speed we can now develop and get results even on complex development together), e.g. project template for VAYRON C# and/or VAYRON C= projects, which basically would map on a VAYRON node/cluster to resolve the graph of objects representing all code associated with whatever scope this project wants to cover, or without scope and the dev 'imports' to the project whatever VCOM types and instances that can be found in the VAYRON node/cluster persistence store(s). NewOrleans already is building capabilities which are meant to amount to those we'll need to make this possible; then custom analyzers and other Roslyn customizations... for IDE dev-time support (starting with not complaining for things which anyway would compile with our Roslyn; then supports for syntax, semantics etc; support for intellisense, which will be made to support dynamically resolved types and even types/instances over the distributed network of VAYRON.. allowing using untyped dynamic vars but with intellisense to enable exploration of the type/object spaces of VAYRON in ways which should build, and with the dynamic code written possibly reinforced in different ways (including more static/direct references) using codegen at build-time). This advanced dynamic space\type\object namespace-like system will be built at the "NewOrleans VAYRON kernel", using Grain Types. In case this isn't specified anywhere, our initial NewOrleans persistence stores are goind to be RavenDB (server), Neo4j locally and AuraDB in the cloud (both Neo4j and RavenDB supporting vector encodings and semantic search), and likely a file database to in which nodes/runtimes can first find their way config wise etc. Possibly also used for caching purpose.

## Addendum: VAYRON Stack Clarification & Build Strategy (2025-12-07)

> **Context:** Comprehensive clarification of the VAYRON stack, component relationships, and the decision to build real infrastructure first.

- VCOM depends on NewOrleans. No NewOrleans loaded, no VCOM. Therefore a project which depends on VCOM is a project which inherently reference/load and manage by itself NewOrleans, without the User (here 'User' means the developer, AI or human, and using the compiler manually or developing via a IDE like Visual Studio 2022) even knowing about NewOrleans, "Silos"/Clusters etc. A project template / system for VAYRON could be designed to make this happen naturally. The "Silos"/Cluster(s) of NewOrleans will make an appearance in the VAYRON ecosystem programmability and config, but as VAYRON concepts rather than Orleans/NewOrleans one, e.g. "VAYRON Nodes" etc.
- VCOM is the VAYRON Component-Object Model and NewOrleans will effectively become a part of VAYRON. When VAYRON is successful and ready to be productized as a second generation which parts will be redistributed, including in big part lowered into our codenamed dotnet fork "dotneXt" (Which then will get its real name/brand etc), NewOrleans and VCOM may be - although in very refactored form - lowered into new systems of "dotneXt", part native, part managed, part virtual (there's a layer over "managed" which I see appearing which is running over managed but at a higher level while gaining access to the layer below-native: illustrative of that is Orleans virtualizing over managed and VCOM virtualizing over Orleans and yet getting direct integrations with the native layer (sub)systems.. creating a vertical shaft/axis which previously wasn't there. This is just a note which could be documented by you somewhere with the rest; it's not something that needs too much definition or plan for at this time).
- So for now: VAYRON = "dotneXt" + NewOrleans + Roslyn Async+ (and probably other Roslyn-based codegenerators) + VCOM + "VARIA" (more on that soon: but you can think of it as "our ActiveX" although very different in every ways and doing a lot more and at different levels) + "VARYON SDK: Project templates + Project Systems + everything needed to develop over VAYRON (not just run VAYRON things) + advanced IDE and Shell integrations, which includes previously talked about (or at least documented and read by you) that IDE/Shell support for VAYRON dynamic advanced namespace-like namesystem allowing exploration/discovery/addressing/use - in a dynamic way not requiring classical "typing"/interfaces" - of anything (e.g. Any Object) in VAYRON (i.e. node(s), domain(s) and federation(s), and VAYRON being designed to become "an Internet of Objects", therefore "in VAYRON (Inter)Network"), doing so creating a hybrid model between Typed and Dynamic/Untyped: "Dynamic Typing". At build-time, these codes using the types integrating with IDE/Shell support for this namesystem can be verified and recoded in safer typed ways, etc.).
- And once VAYRON is successful: We reshaped everything as a fundamental platform based on dotnet, the first real fork/alternative to dotnet since MONO, and keeping interop with the dotnet ecosystem while adding to it a sane evolutionary pressure edge.. which could end up being something akin to "Fedora to the Red Hat": An Avant-guard for dotnet, with full collaboration of Microsoft and the .NET Foundation (let alone Azure: that's $$$ to them, as a potential differentiator to Azure from other cloud).
- So this NewOrleans running behind the curtain at runtime in VAYRON, to start with can be 1 'Silo' and a running process would be 1 VAYRON Node. Default configs hardcoded for now. When the time comes and we design how this is all exposed in "VAYRON's World", this will evolve.
- VCOM mechanisms/infras/etc will be built over mostly over NewOrleans and in C#: a mix of regular managed types and grain types acting as components/services of the "VAYRON Kernel", which VCOM will be both using and a part of.
- Same for the VAYRON namesystem, which we can give a codename from now on for clarity in discussion and documentation: VNS. The V in VNS could stand for VAYRON for now, but may stand in the future for VARIA or VIRTUAL (e.g. Varia Name System; Virtual Name System).
- VAYRON/VCOM - as said/documented - should have code written for/against it (and some of its own code) persisted/versioned through and loaded from VCOM Types/Objects. Under the hood, this persistence etc will be handled by NewOrleans: this is just some more fields/members of some grain type/grain backed VCOM Objects. Binaries are also to be cached in the same way, for performance reasons, but then it's CODE as first-Class: VCOM Objects "own" their codes and this code is always (for now) accessible to them, mutable and reloadable at runtime.

**On Async+ and build order:**

When things are presented like that, some things may become obvious:
- Async+ and continuations etc should be kept in mind while working on VCOM, the VNS etc, but **they shouldn't be retouched and completed until a sufficient subset of those things described above are realized**. There's was no DCOM and COM+ or ActiveX before COM. Meanwhile any "auto-persistence" can be explored in other patterns, paradigms. Many are possible without Async codegen anyway.
- We already have dotnext fully compilable and distributable, and with an automatized workflow which integrates both "everything Roslyn+ (our Roslyn..) + everything dotnext runtime" directly into Visual Studio 2022.. and this works very well. Terminal access to dotnext also work, obviously. I'm thinking we should develop from the start over this, build our VAYRON SDK, project templates, project system integration into VS2022, etc. **We aren't chasing "PoC" (Proof of Concepts): we're developing the whole thing from A to Z. So why build things in some orders to give us illusion of progressing faster than we are rather than investing in our workflow and "framework" over which to build the rest?**

**On VNS vs VCOM resolution (clarification):**

"VCOM reference resolution depends on VNS" - Oh. I didn't even realized that it could be the case. Is it though? It depends on the design we'll adopt. But **this will likely be the case in some contexts**, not all. In the case of Async+ codegen, those references would be VCOM level ones which resolution depends then on the Grain types of the VAYRON kernel, not on the VNS. The VNS is having its own references and likely mostly at the "VARIA" level. It's akin to the difference between MAC addresses, IP addresses, "and domain names": The VNS is - as its name rightfully intuitively suggest - **more like the DNS**.
